Case study: Agent Auditor watching its own chat agent

I ran Agent Auditor against the demo agent in this repo (Auditor Chat) for about a day, switching between many models and providers, and read what the dashboard reported. This is what it showed, including where it fell short. Numbers come from the dashboard on 7 October 2026 (agent chat-agent, last 7 days). The run counts are small, so treat this as a worked example and not a benchmark.

1. The agent

  • What it does: a ChatGPT-style assistant that answers questions, uses a calculator and web search, and reads files. Every chat turn is recorded as one run (a step per model call and per tool call). I was the only user.
  • Stack: Python standard-library server, with the model chosen per conversation. Each model is registered as its own agent version (chat-<hash>), so the dashboard can tell models apart. Models tried:
  • Gemini (gemini-2.5-flash, gemini-2.5-flash-lite, gemini-3.5-flash)
  • AIRouter (openai/gpt-5-nano)
  • Nabh (mistral-7b-instruct)
  • Indos (Deepseek/deepseek-v4-flash, openrouter/meta/llama-4-scout, gemini/gemini-3.8-flash)
  • OpenRouter (nvidia/nemotron-3.5-lightning:free)
  • Mistral (mistral-small-latest)
  • Ollama on my PC (llama3.1)
  • How it was connected: the chat server posts each turn to Agent Auditor through the Python SDK. No change to the agent's logic was needed.

Each of the 62 flagged runs (24 errored plus 38 answered badly) gets one most-likely cause.

The headline number looks alarming, and the dashboard's own breakdown shows why it is misleading. Most flagged runs were slow, not wrong. For example, one run (e25be41e, AIRouter gpt-5-nano) answered the question correctly but took 23 s against the 10 s latency budget, so it was flagged as a slow run. Another model (deepseek-v4-flash) was flagged at 10.2 s for the same question. The rest were provider problems: timeouts, rate limits and rejected keys.

3. Failures turned into regression tests

  • Converted: 4 regression tests, all from the latency check. They came from the questions "Explain RAG simply", "which is the best ai tool for content creating", "what is this image" and "which is the best ai tool for generating ai contents". Three of them had been seen 3–4 times each, which is what the "Seen" column counts.
  • Replayed: not yet. The page shows "No replays yet". Replay needs the SDK to call the agent from Python, and I did not run that step for this case study.

4. A change gated by a canary

First attempt (7 October): no verdict. I used the Canary page to compare the active version (chat-8a662e2d) with three candidates. All four checks ended continue, "only N canary runs so far; need 20" (N was 0, 2, 3 and 0). That is the correct behaviour: with too few runs on both sides, the tool says so instead of guessing. It also meant my chat, which sends all traffic to production, never gave a candidate enough canary runs.

Second attempt (9 November): a real verdict. I wrote bench/canary.py, which asks a baseline model and a candidate model the same 24 questions, records them as production and canary runs, scores them, and asks the Auditor for a verdict. A first candidate (gemini-2.5-flash-lite) was refused by Google ("not available for this kind of request"), so it got 4 runs and the verdict was again continue. With a working candidate:

Answered / errored 24 / 0 24 / 0

Verdict: HOLD.

Check Result
evals pass: no significant pass-rate regression
latency fail: 3.16x the baseline (KS p = 4e-9)
causes pass: no failure cause became more common
drift warning: latency differs; "may come from routing rather than the candidate"
replay skipped: no regression replay for the candidate version
change pass: likely a model change (moderate), since only the model changed

How to read it: the candidate was not wrong or broken, it was slower. The Auditor held it back instead of rolling it back, because its rollback threshold is 4x on latency and this was 3.16x, and nothing else regressed. That is the decision I would have made by hand, but I got it with numbers and a named check behind it.

Third attempt (11 November): all three verdicts. I wrote bench/verdicts.py, which runs three checks on real models with the same 24 questions each and writes docs/real-verdicts.md. The numbers below are from that report.

Check Baseline (production) Candidate (canary) Median 95th percentile Verdict
A slower candidate Indos deepseek-v4-flash AIRouter gpt-5-nano 2.6 s vs 4.7 s 5.0 s vs 7.6 s promote (I expected hold)
A broken candidate (planted fault) Indos deepseek-v4-flash the same model through a wrong address 2.6 s vs 2.1 s 5.0 s vs 2.1 s rollback
A faster candidate AIRouter gpt-5-nano Indos deepseek-v4-flash 4.3 s vs 1.9 s 8.6 s vs 4.2 s promote
  • Rollback worked, but the fault was planted. All 24 candidate calls failed. Evals failed on four checks and a new cause, llm_error, went from 0% to 100% of runs. This shows that the gate stops a broken release, not that a real model failed alone.
  • Promote worked. The faster model was 0.47x the baseline's time and nothing got worse.
  • The first check surprised me. The same two models that earned a hold on 9 November (3.16x slower) earned a promote today, because the gap was only 1.78x. The default policy only fails latency at 2x the baseline; between 1.3x and 2x it raises a warning, and warnings alone do not stop a promote. So the Auditor promoted a candidate that was 78% slower, with two warnings (latency, and an evals difference that was not significant) in the report. That is the policy working as written, and also a sharp edge. bench/verdicts.py now judges every check a second time with warnings set to block, using the same runs, and prints both verdicts side by side.
  • The strict setting is blunt. The drift check also warns when a candidate is faster, so a strict policy can hold an improvement. A warning that knows which direction is bad is on the roadmap.
  • Speed moved between days. The same pair of models gave 1.7 s vs 4.4 s on 9 November and 2.6 s vs 4.7 s on 11 November, which is why 24 runs per side is a thin basis for a hard line.

5. What it caught that I would have missed

  • Slow-but-correct answers were being counted as failures. Reading the answers alone, many looked fine. The latency check and the "What to change" box showed that the real problem was model speed, not answer quality.
  • A local model that was effectively unusable. Runs on Ollama llama3.1 took 600 to 854 s each, and two timed out at about 600 s. I had no feel for that on my own PC until the Runs page listed it.
  • Failures clustering by provider. One Gemini model failed in under half a second with "not available" (a model that was gone), which is a different problem from the timeouts and rate limits. The per-cause tags kept these apart.
  • The need for a fix outside the prompt. Several of the causes could not be fixed by editing prompts. This led me to add automatic routing around slow and rate-limited models to the chat app.

6. What did not work

  • The Fixes page had nothing it could apply. For 37 failed runs it proposed three items (investigate slow run, handle model rate limits, investigate tool error), all marked manual, because each "needs a code or infrastructure change, not a setting". That is by design, but it means the tool could not fix this agent on its own.
  • The only real rollback used a planted fault (section 4). I have not seen a real model break on its own in a canary, and I chose the thresholds myself, so how they behave on other agents is untested. In a test with fake model servers, an identical candidate was promoted, which matches the real promote above.
  • The canary could not see wrong-but-well-formed answers. In a test with fake model servers and no expected answers on the runs, a candidate that answered "I am not sure" to everything was promoted, because the checks then looked only at errors and speed. That led to the answer-correctness work: a gives_an_answer check that catches non-answers with no labels, and an optional model judge for confident wrong answers. See answer-correctness.md for what each one does and does not catch. The real-model comparisons above did carry expected answers.
  • Benchmark scores are shaky at this size. The Benchmark page ranked nvidia/nemotron-3.5-lightning:free at 83% and mistral-small-latest at 0%, but the 0% most likely reflects rate-limited calls, not poor answers, and Gemini and Ollama had no checked answers. Do not read it as a model ranking.
  • Root-cause "tied to one version" was empty. It needs two versions with enough runs each, and my runs were spread across a dozen or so versions.
  • No source-document analysis. The chat does not report document ids for retrieved results, so that check was skipped.
  • The regression tests are only latency tests, so they say nothing about answer correctness.
  • See also "Known limitations" in the README.

7. Reproduce it

  • Agent Auditor 0.12.1, SQLite database (agent_auditor.db), Windows, Python 3.11 or newer.
  • Start everything with powershell -ExecutionPolicy Bypass -File .\run-all.ps1, put your provider keys in .env, and chat with several models in the chat app (it records each turn automatically).
  • For all three verdicts on real models, keep that running and, in a second window, run python bench/verdicts.py (about 20 minutes; the report is written to docs/real-verdicts.md). For a single comparison, use python bench/canary.py --baseline "<provider:model>" --candidate "<provider:model>" --pause 2. python bench/canary.py --list shows the ids. It needs two working models and takes about 10 to 15 minutes.
  • Open http://127.0.0.1:8000/dashboard, select chat-agent, then use Overview, Failures, Root causes, Regression tests, Fixes and Canary. Your numbers will differ, because they depend on your keys, models and the day's rate limits.
  • To validate the tool itself against planted faults instead of live traffic, run python validation/run_validation.py --dry-run.
